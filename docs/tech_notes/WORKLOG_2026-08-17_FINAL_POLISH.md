# Worklog — финальная полировка и сквозной аудит

**Дата:** 2026-08-17  
**Граница:** живые V2-маршруты, курсы, отчётность, RBAC и сквозные проверки.  
**Исключено по решению продукта:** отдельный веб-центр уведомлений и встроенный чат; остаются Telegram-уведомления и контекстные подтверждения.

## Шаг 1 — согласование границ

- **Цель:** исключить из релизного плана ненужные веб-сущности.
- **План:** не создавать центр уведомлений, чат или новый дашборд; проверить, что существующие дашборды получают данные из реальных действий.
- **Затрагиваемые файлы:** без изменения кода.
- **Критерий готовности:** план не содержит отдельной страницы уведомлений или чата.
- **Результат:** подтверждено пользователем; границы применены ко всем последующим проверкам.
- **Риски:** архивные и compatibility-маршруты нельзя принимать за живые экраны.
- **Следующий шаг:** выборочная V2-регрессия.

## Шаг 2 — выборочная V2-регрессия

- **Цель:** убедиться, что уже переведённые V2-контуры не регрессировали до нового аудита.
- **План:** проверить CRUD курса, снятые веб-уведомления и снятый веб-чат; скомпилировать курсы и проверить diff.
- **Затрагиваемые файлы:** без изменения кода; `tests/v2/test_role_lifecycle_recovery.py`, `app/courses/`.
- **Критерий готовности:** тесты проходят, Python компилируется, `git diff --check` чист.
- **Результат:** 3 passed, 65 deselected; компиляция и проверка diff прошли.
- **Риски:** выборка не заменяет полный регресс.
- **Следующий шаг:** полный V2-регресс с остановкой на первой ошибке.

## Шаг 3 — найден P0-дефект административной матрицы

- **Цель:** найти реальные серверные падения.
- **План:** запустить полный V2-регресс, локализовать первопричину и исправить контракт, а не маскировать один вызов.
- **Затрагиваемые файлы:** `core/audit_logger.py`, `app/admin/routes.py`, `tests/v2/test_admin_functional_v2.py`.
- **Критерий готовности:** `/admin/permissions/toggle` сохраняет право и возвращает успешный ответ без HTTP 500.
- **Результат до исправления:** полный тест остановился на `test_permissions_matrix_reads_and_persists_real_role_permissions`: маршрут вызывает отсутствующий `AuditLogger.log_event`, а сам обработчик ещё и не сохраняет `RolePermission`.
- **Риски:** такой же старый контракт `log_event` используется при создании пользователя в админке; совместимость должна быть централизованной.
- **Следующий шаг:** восстановить совместимый метод аудита и реальное сохранение права с валидацией входных данных.

## Шаг 4 — исправление сохранения прав и совместимости аудита

- **Цель:** закрыть блокирующий 500 и восстановить реальную запись права в БД.
- **План:** добавить совместимый `log_event` поверх единого очередного аудита; валидировать роль/право/тип флага; создать или обновить `RolePermission` транзакционно.
- **Затронутые файлы:** `core/audit_logger.py`, `app/admin/routes.py`, `tests/v2/test_admin_functional_v2.py`.
- **Критерий готовности:** успешный toggle возвращает фактическое значение, некорректный payload отклоняется, аудит не роняет HTTP-обработчик.
- **Фактические изменения:** добавлен совместимый `AuditLogger.log_event`; toggle теперь проверяет входные данные, сохраняет запись `RolePermission`, возвращает `enabled`; добавлена регрессия невалидного payload.
- **Проверка:** выполняется следующим шагом.
- **Риски:** legacy-вызов `log_event` при создании пользователя теперь также проходит через единый аудит; это намеренное восстановление совместимости.
- **Следующий шаг:** прогнать admin-набор и затем полный V2-набор.

## Шаг 6 — импорт и экспорт: восстановление связей ученик → урок

- **Цель:** исключить потерю привязки уроков при переносе экспортированного JSON в другую БД.
- **План:** добавить в новый экспорт стабильный ключ ученика и ключ на уровне урока; на импорте построить отображение экспортного ключа на фактический `student_id`; сохранить обратную совместимость для старых файлов с числовым `student_id`.
- **Затрагиваемые файлы:** `app/main/routes.py`, новая или расширенная V2-регрессия импорта/экспорта.
- **Критерий готовности:** урок из свежего экспорта связывается с импортированным учеником независимо от нового локального ID; старый JSON не ломается.
- **Результат до исправления:** экспорт не содержит идентификатора ученика, совместимого с новой БД; импорт урока проверяет старый числовой `student_id`, поэтому перенос между БД теряет уроки.
- **Риски:** импорт — административная операция; нельзя переиспользовать логин/`platform_id` без контроля коллизий. Приоритет — только связь ученик/урок и отсутствие скрытой подмены данных.
- **Следующий шаг:** проверить модель `Student`, реализовать совместимый ключ и тестовый контракт.

## Шаг 7 — совместимый формат импорта/экспорта

- **Цель:** сделать экспорт самодостаточным для восстановления связи уроков с учениками.
- **План:** ввести версию формата и payload-scoped ключи, построить mapping до импорта уроков, сохранить fallback старого числового ID.
- **Затронутые файлы:** `app/main/routes.py`, `tests/v2/test_admin_functional_v2.py`.
- **Критерий готовности:** импорт создаёт урок с фактическим ID импортированного ученика, а не с исходным ID из другого окружения.
- **Фактические изменения:** экспорт теперь имеет `export_schema_version: 2`, `student_source_id` и `student_key`; импорт отображает их на вновь созданный/найденный профиль до записи уроков. Старые файлы используют прежний `student_id` только как fallback. Добавлена регрессия полного восстановления одной связи.
- **Проверка:** ожидает восстановления Python-окружения; static diff будет проверен отдельным шагом.
- **Риски:** старый файл без ключа может быть восстановлен полностью только в той же БД — это неизбежно, потому что в нём нет данных для надёжного сопоставления.
- **Следующий шаг:** дополнить CHANGELOG и продолжить live route/template audit.

## Шаг 9 — каноничные подтверждения опасных действий

- **Цель:** заменить остатки системных confirm-окон, не ослабляя защиту опасных действий.
- **План:** сделать подтверждение очистки формы асинхронным, а удаление задания генератора — await-диалогом `BooNotify`.
- **Затронутые файлы:** `templates/accepted.html`, `templates/task_generator.html`.
- **Критерий готовности:** отмена не отправляет форму и не удаляет задачу; без `BooNotify` опасное действие блокируется.
- **Фактические изменения:** форма очистки принятых задач отменяет submit, открывает V2-модалку и отправляется только после явного согласия. Удаление задачи из генератора использует тот же диалог; fallback безопасно отменяет действие.
- **Проверка:** `git diff --check`, повторный поиск `window.alert/confirm/prompt` в рабочих шаблонах и `node --check static/lesson-studio-os.js` успешны.
- **Риски:** в изолированных архивных и preview-макетах старые диалоги намеренно не менялись — это не достижимые пользователем live-экраны.
- **Следующий шаг:** завершить реестр live-рендеров и составить перечень фактической готовности/ограничений для релиза.

## Шаг 10 — полнота резервной копии учеников и уроков

- **Цель:** не терять уроки неактивных учеников при экспорте и повторном импорте.
- **План:** включить в V2-экспорт всех учеников вместе с признаком активности; восстановить этот признак при создании профиля; сохранить устойчивую связку урока с учеником.
- **Затрагиваемые файлы:** `app/main/routes.py`, `tests/v2/test_admin_functional_v2.py`.
- **Критерий готовности:** экспортируемый файл содержит каждого ученика, на которого ссылается урок; импорт не превращает архивный профиль в активный и не отбрасывает его уроки.
- **Результат до исправления:** экспорт включал только активных учеников, но выгружал все уроки. Урок неактивного ученика оказывался без современного ключа связи и мог пропасть при переносе в другую БД.
- **Риски:** импорт не должен подменять статус уже существующего профиля; признак активности применяем только при создании нового профиля.
- **Следующий шаг:** расширить контракт экспорта и добавить покрытие сценария неактивного ученика.

### Результат шага 10

- **Фактические изменения:** экспорт теперь включает всех учеников и их признак `is_active`; урок сохраняет ключ своего владельца независимо от активности профиля. При создании нового профиля импорт уважает сохранённый признак активности, но не меняет уже существующие профили.
- **Проверка:** `git diff --check` завершился без замечаний. Добавлена регрессия для архивного ученика с историческим уроком.
- **Риски:** запуск pytest всё ещё заблокирован отсутствующим исполняемым Python в локальном `venv`; тест добавлен, но пока не помечается как выполненный.
- **Следующий шаг:** завершить статический аудит доступных live-рендеров и запретить реальное использование legacy-шаблонов через регрессионные контракты.

## Шаг 25 — Стабилизация административных V2-операций

- **Цель:** устранить реальные 500-ошибки административных операций, найденные полным V2-набором, и не оставлять сломанными вспомогательные экраны.

### Первый исправленный сбой

- **Причина 500:** новый V2-экспорт ошибочно обращался к `Course.course_id` и `Course.status`; фактическая модель использует `Course.id` и `Course.is_active`.
- **Изменение:** сериализация курсов переведена на реальный контракт и отдаёт совместимый статус `active`/`archived`.
- **Проверка:** точечный тест будет повторён до перехода к следующему административному сбою.

### Результат первого исправления

- **Проверка:** `tests/v2/test_admin_functional_v2.py::test_diagnostics_and_export_use_real_platform_data` — **1 passed**.
- **Риск:** экспорт больше не падает на курсах; остальные независимые ошибки админского набора ещё должны быть проверены отдельно.
- **Следующий шаг:** выполнить весь административный V2-набор с остановкой на следующем первом сбое.

### Второй исправленный сбой

- **Причина 500:** endpoint создания темы безусловно вызывал `request.get_json()`, поэтому стандартная V2-форма получала `415 Unsupported Media Type`, преобразованную в 500.
- **Изменение:** endpoint поддерживает оба корректных транспорта: JSON API и `request.form`; невалидный/отсутствующий JSON больше не ломает форму.
- **Проверка:** повторяется тест создания темы и проверки задания, затем набор продолжится до следующей причины.

### Третий исправленный сбой

- **Причина:** формирователь задач подтверждал успешное сохранение, но писал статус в несуществующее поле `Tasks.review_status`; запись `TaskReview` не создавалась.
- **Изменение:** реализован идемпотентный upsert `TaskReview` с task id, статусом и текущим проверяющим; для отсутствующей задачи возвращается честный 404.
- **Проверка:** повторяется V2-сценарий создания темы и сохранения проверки.

### Четвёртый исправленный сбой

- **Причина:** V2-модалка отправляла `full_name`, `email` и `is_active=false`, а старый handler ожидал обязательный `username`, понимал только checkbox `on`, игнорировал email и всегда отвечал HTML-redirect.
- **Изменение:** JSON-запрос модалки получает JSON-ответ; full name разбирается в профиль, email обновляется с проверкой уникальности, username остаётся прежним, если его не передали, а boolean-поля обрабатываются явно.
- **Совместимость:** серверная форма сохраняет существующий redirect и flash-flow.
