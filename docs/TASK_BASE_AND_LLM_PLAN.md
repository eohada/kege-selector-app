# План: эталонная база заданий и LLM (тренажёр)

Подробный пошаговый план: структура эталона, правила сложности, фазы от текущей базы до эталонной разметки, обучения LLM (помощник + создатель заданий) и детектора поведения. Каждый пункт разложен по полочкам.

---

## 1. Текущее состояние (что есть сейчас)

### 1.1. Типы заданий ЕГЭ

- Файл: `data/analytics_kege_difficulty.json`.
- Для каждого номера 1–27 заданы:
  - `task_number`, `topic`, `node_code`, `base_rating`, `exam_points`, `complexity_tier`.
- `complexity_tier`: Trivial, Basic, Intermediate, Advanced, Hard, Expert, Boss — **на уровне типа**, не отдельной задачи.
- Используется: сид узлов знаний, API аналитики, прогноз балла.

### 1.2. База заданий (Tasks)

- Таблица `Tasks`: `task_id`, `task_number`, `content_html`, `answer`, `knowledge_node_id` и др.
- Привязка к узлу: по `knowledge_node_id` → узел имеет один `base_rating` на весь тип.
- **Нет:** поля «сложность этой конкретной задачи» (лёгкое/среднее/тяжёлое).
- Итог: все задачи одного типа в аналитике считаются одинаковой сложности.

### 1.3. Тренажёр и знания

- Каталог `trainer_knowledge/tasks/`: JSON по отдельным задачам (`task_id`, `task_number`, `reference_solution`, `hint_ladder`, `common_mistakes`, `tests`).
- LLM в тренажёре не обучена на этих данных; заготовки можно использовать как основу эталонов.
- Нет единого формата «эталонный прототип по типу × уровень сложности».

### 1.4. Аналитика и детектор

- `app/analytics/engine.py`: обновление рейтинга по узлу после проверки ответа, приём `time_spent_sec`.
- При правильном ответе и времени < 10 сек: `k_factor` умножается на 0.1 (рейтинг почти не растёт).
- **Нет:** проверки «задача тяжёлая»; нет категорий «Невнимательность» / «Списывание»; нет проверки «время < 5 сек + неверный ответ».

## 2. Целевое состояние (к чему идём)

### 2.1. Эталон

- По каждому типу (1–27) — набор эталонных прототипов с явной сложностью: лёгкое / среднее / тяжёлое.
- В прототипе: формулировка, эталонное решение, типовые ошибки, лестница подсказок.
- Хранение: единый формат (JSON), один каталог или расширение текущего `trainer_knowledge`.

### 2.2. База заданий

- У каждой задачи в БД (или в справочнике) — уровень сложности: лёгкое / среднее / тяжёлое.
- Разметка согласована с правилами и эталонами; при добавлении новых заданий — правило или LLM + проверка человеком.

### 2.3. LLM

- Обучена на эталонах.
- **Помощник:** подсказки в тренажёре по лестнице, без полного решения.
- **Создатель/классификатор:** по новой формулировке предлагает тип задания, уровень сложности, черновик разбора; сохранение только после проверки человеком.

### 2.4. Детектор

- Быстрый провал: < 5 сек, неверный ответ → «Невнимательность».
- Быстрый успех на тяжёлой задаче: < 10 сек, верный ответ → не завышать рейтинг, при необходимости метка «Списывание / Знает наизусть».
- Используется разметка сложности конкретной задачи (тяжёлое), а не только тип.

## 3. Структура эталона (подробно)

### 3.1. Уровни сложности задачи

Три уровня для **конкретной задачи** (инстанса):

| Уровень   | Код (пример) | Назначение | Когда использовать в подборе |
|-----------|----------------|------------|------------------------------|
| Лёгкое    | `easy`         | Разогрев, тренировка, автопроверка | Начало темы, закрепление |
| Среднее   | `medium`       | Основная практика | Обычные уроки и ДЗ |
| Тяжёлое   | `hard`         | Контроль, экзамен, сложный срез | Проверочные, экзамен |

Связь с текущим `complexity_tier` типа (Trivial/Basic/…/Boss): лёгкое задание обычно из типа с низким tier или нижней части диапазона; тяжёлое — из высокого tier или верхней части. Правила задаём явно в конфиге/таблице по `task_number`.

### 3.2. Поля эталонного прототипа (по полочкам)

Один эталонный прототип = один JSON-объект (или запись в БД). Рекомендуемые поля:

| Поле | Обязательность | Описание | Пример / формат |
|------|----------------|----------|------------------|
| `task_number` | да | Номер задания ЕГЭ (1–27) | `24` |
| `node_code` | да | Код узла знаний из analytics_kege_difficulty | `"STRINGS-HARD"` |
| `topic` | да | Название темы (для людей и LLM) | `"Обработка символьных строк"` |
| `difficulty` | да | Уровень: `easy` / `medium` / `hard` | `"hard"` |
| `statement_html` или `statement_text` | да | Формулировка задачи (как в КЕГЭ) | HTML или plain text |
| `reference_solution` | да | Пошаговое решение + итоговый ответ | Текст или структура (шаги + ответ) |
| `correct_answer` | по необходимости | Итоговый ответ для автопроверки | строка/число |
| `common_mistakes` | да | 1–3 типовые ошибки | массив строк |
| `hint_ladder` | желательно | Подсказки по уровням 1–3 | массив `{ "level": 1, "hint": "…" }` |
| `source` | опционально | Откуда задача (открытый банк, год) | для трассировки |
| `id` / `slug` | опционально | Уникальный идентификатор прототипа | для ссылок и версий |

Файловая структура (пример):

- `data/reference_prototypes/` или `trainer_knowledge/reference/`
  - по типам: `by_type/01_GRAPH-BASICS.json` (массив прототипов по типу),  
  - или по одному файлу на прототип: `by_type/01/easy_001.json`, `01/medium_001.json`, `01/hard_001.json`.

### 3.3. Хранение сложности в БД (решение: вариант A)

**Решение:** однозначно выбираем **вариант A** — поле непосредственно в таблице `Tasks`.

**Почему:** сложность — такое же фундаментальное свойство задачи, как текст условия. Хранение в `Tasks` избавляет от лишней нагрузки: при подборе заданий на урок не нужен JOIN с отдельной таблицей.

**Реализация:**

- Добавить в модель `Task` (таблица `Tasks`) поле **`difficulty_level`**.
- Тип поля: **Enum** (easy / medium / hard) или **Int** (см. маппинг ниже). При использовании Int удобно хранить значение 1–10 для совместимости с градацией «лёгкое / среднее / тяжёлое» и формулами рейтинга.
- Миграция: добавить колонку (nullable на период заполнения), затем заполнить в Фазе 2.

### 3.4. Маппинг Easy / Medium / Hard для БД и AnalyticsEngine (Elo)

Движок аналитики (Elo) оперирует числовым рейтингом задачи. Нужен однозначный перевод уровня сложности в значение для формул.

**Таблица маппинга (утвердить в Фазе 0):**

| Метка (для методистов) | Значение в БД (`Task.difficulty_level`) | Рейтинг задачи для Elo (в движке) |
|------------------------|----------------------------------------|-----------------------------------|
| **Easy** (лёгкое)      | 1–3 (или код 1)                        | `Base_Node_Rating - 100`          |
| **Medium** (среднее)   | 4–7 (или код 2)                        | `Base_Node_Rating`                |
| **Hard** (тяжёлое)     | 8–10 (или код 3)                       | `Base_Node_Rating + 150`          |

- **Base_Node_Rating** — базовый рейтинг узла знаний (`KnowledgeNode.base_rating`), к которому привязана задача.
- Итог: методисты оперируют понятными метками («эта задача сложная»), движок получает числа для формул. В `AnalyticsEngine` при расчёте вероятности и обновлении рейтинга использовать рейтинг задачи из этой таблицы (а не только `base_rating` узла), если у задачи заполнено `difficulty_level`.

### 3.5. Хранение лестницы подсказок (hint_ladder) в БД

В плане описан JSON-формат подсказок в эталонных прототипах. Чтобы хранить подсказки у конкретной задачи в БД (для тренажёра и LLM):

- В таблице **`Tasks`** (или в связанной таблице **`TaskAssets`**, если подсказки вынесены в отдельную сущность) добавить поле типа **JSONB** для хранения лестницы подсказок.
- **Имя поля:** например `hints` или `hint_ladder`.
- **Структура JSON:** массив объектов с уровнями и текстом подсказки:
  ```json
  [{"level": 1, "text": "Направление / идея..."}, {"level": 2, "text": "Структура решения..."}, {"level": 3, "text": "Наводка без полного решения..."}]
  ```
- **Пример в модели (SQLAlchemy, PostgreSQL):**
  ```python
  # В модели Task (Tasks)
  hints = db.Column(postgresql.JSONB)  # или db.JSON с поддержкой JSONB в PostgreSQL
  ```
- При использовании SQLite или иной БД без JSONB — хранить как `db.JSON` или `db.Text` с валидным JSON; при миграции на PostgreSQL при необходимости сменить тип на JSONB.

## 4. Правила разметки сложности (подробно)

### 4.1. Кто задаёт правила

- Владелец продукта / методист: по каждому типу задания (1–27) решает, по каким признакам задача считается лёгкой, средней или тяжёлой.
- Разработчик: переносит правила в конфиг или код (таблица, JSON, скрипт).

### 4.2. Примеры признаков для правил

- **Статистика решений (приоритетный сигнал):** если по задаче есть исторические данные (кто решал, верно/неверно), доля успешных решений — лучший критерий сложности, чем только текст условия или мнение LLM. Примеры: ~90% решили → Easy; ~20% → Hard; промежуточные значения → Medium. Пороги утвердить и использовать как основной или дополнительный сигнал при разметке (см. Фазу 2).
- **Объём условия:** короткое / среднее / длинное (пороги по числу символов или абзацев).
- **Число шагов в решении:** 1–2 шага → easy, 3–5 → medium, 6+ или неочевидная цепочка → hard.
- **Типовые ошибки:** если в задаче заложен «капкан» из списка типовых ошибок эталона — сдвиг в сторону medium/hard.
- **Экспертная метка:** эталонные прототипы уже размечены (easy/medium/hard); по ним калибруют автоматические правила.
- **Базовый рейтинг узла:** для типа с высоким `base_rating` чаще тяжёлые; с низким — чаще лёгкие (при необходимости — веса по диапазонам).

### 4.3. Результат правил

- Таблица или конфиг: по `task_number` — описание правил (или пороги), как вычислить/предсказать `easy`/`medium`/`hard` для новой или существующей задачи.
- Опционально: скрипт, который по формуле/порогам выставляет черновую сложность; человек выборочно проверяет и правит.

### Фаза 5. Детектор поведения

Цель: учитывать «быстрый провал» и «быстрый успех на тяжёлом» в аналитике и не искажать рейтинг.

#### 5.1. Модуль классификации события

- [ ] Создать модуль: например `core/analytics/behavior.py` или `app/analytics/behavior.py`.
- [ ] Вход: `task_id`, `is_correct`, `time_spent_sec`, при необходимости `user_id`, `submission_id`.
- [ ] Получить сложность задачи: из БД (поле в Tasks или отдельная таблица) или из справочника; если нет разметки — считать задачу «не тяжёлой» для детектора.
- [ ] Правила:
  - если `time_spent_sec < 5` и неверный ответ → категория `carelessness` (Невнимательность);
  - если `time_spent_sec < 10`, правильный ответ и задача **тяжёлая** → категория `fast_success_hard` (Списывание / Знает наизусть).
- [ ] Выход: категория события (или «норма») и флаг «не увеличивать рейтинг» для быстрого успеха на тяжёлом.

#### 5.2. Интеграция с engine

- [ ] В `app/analytics/engine.py` (или в месте вызова `process_submission`) перед обновлением рейтинга вызвать детектор.
- [ ] Если детектор вернул «быстрый успех на тяжёлом»: применить ослабление K (как сейчас при времени < 10 сек, но только для задач с разметкой «тяжёлое»).
- [ ] Если детектор вернул «быстрый провал»: при желании не менять рейтинг или менять слабее; опционально только записать категорию в события.
- [ ] Сохранять категорию в аналитике (например, в `AnalyticsEvent` добавить поле `behavior_category` или писать в отдельную таблицу событий детектора).

#### 5.3. Константы и настройки

- [ ] Пороги вынести в конфиг или константы: 5 сек для провала, 10 сек для успеха, список категорий.
- [ ] Документировать: при отсутствии разметки сложности «тяжёлое» не считается (не штрафуем за быстрый успех).

#### 5.4. Отчёты (опционально)

- [ ] При желании: отчёт по ученику или по группе — сколько событий «Невнимательность», сколько «Быстрый успех на тяжёлом» (для методиста/преподавателя).

#### 5.5. Чек-лист Фазы 5

- [ ] Модуль детектора реализован и покрыт правилами из спецификации.
- [ ] Рейтинг не завышается при быстром успехе на тяжёлой задаче.
- [ ] Быстрый провал классифицируется; при необходимости учтён в рейтинге или только в логах.
- [ ] Сложность для детектора берётся из разметки базы (Фаза 2).

## 6. Риски и ограничения
