# MMR/Elo System QA Guide (BooStudy)

> Полный гайд для тестировщика, который **раньше не работал** с этой системой.
> Формат подходит для Obsidian (заголовки, чеклисты, таблицы, callouts).

---

## 1. Что это за система

MMR-система — это модель рейтинга ученика по заданиям, где после каждого проверенного ответа рейтинг меняется на `+` или `-`.

Система нужна для:

- более точной оценки прогресса ученика;
- адаптивного подбора задач;
- прозрачной аналитики (история изменений с объяснимыми коэффициентами).

---

## 2. Базовые термины

## 2.1 `MMR`

- Числовой рейтинг ученика.
- Есть:
  - глобальный/узловой (`UserMastery`) — если задача привязана к узлу знаний;
  - по типу задания 1..27 (`UserTaskMMR`) — основной слой для практики КЕГЭ.

## 2.2 `ΔMMR` (дельта)

- Изменение рейтинга за одно действие (одну проверенную попытку).
- Может быть положительным (верно) или отрицательным (ошибка).

## 2.3 Калибровка

- Ранний этап, когда система быстрее “подстраивается” под уровень ученика.
- Идет **по каждому типу задания отдельно** (например, отдельно для №5, отдельно для №17).

## 2.4 `AnalyticsEvent`

- Лог-событие на каждую проверенную попытку.
- Хранит: результат, время, коэффициенты, `ΔMMR`, сложность, режим и т.д.

---

## 3. Формула и логика расчета

Фактически используется:

`ΔR = D × C_time × C_attempt × C_calibration × delta_scale`

Далее применяется ограничение (каппинг):

- максимум прироста за событие;
- максимум потери за событие.

---

## 4. Коэффициенты и константы (что за что отвечает)

## 4.1 Вес сложности `D`

- База: `800`
- Стандарт: `1500`
- Хард: `2200`

Чем выше сложность, тем больше потенциальная дельта.

## 4.2 Коэффициент времени `C_time`

Считается по отношению:

`time_ratio = effective_time_sec / T_ref`

где `T_ref` — эталонное время для номера задания.

Диапазоны:

- `fast`: `ratio < 0.8` -> `1.2`
- `normal`: `0.8 <= ratio <= 1.5` -> `1.0`
- `slow`: `ratio > 1.5` -> `0.7`
- анти-спираль (слишком быстро): `ratio < 0.15`
  - верный ответ -> `0.0` (награда срезается)
  - неверный ответ -> `1.5` (усиление штрафа)
- AFK clamp: если `ratio > 3.0`, время режется до `3.0 * T_ref`.

## 4.3 Коэффициент попытки `C_attempt`

Для верных ответов:

- 1-я попытка -> `1.0`
- 2-я -> `0.5`
- 3+ -> `0.5`

Для неверных ответов:

- `1.0`

## 4.4 Калибровочный множитель `C_calibration`

По каждому `task_type`:

- первые 5 решенных -> `x3`
- следующие 5 -> `x2`
- далее -> `x1`

> Важно: именно поэтому по разным номерам в один момент могут быть разные `c`.

## 4.5 Стабилизация дельты

Это 2 механизма, чтобы не было “безумных” прыжков:

1. `delta_scale = 0.02`  
  - просто масштабирует сырую дельту вниз в 50 раз.
2. `delta_cap`  
  - `max_gain = 180`
  - `max_loss = 180`
  - даже если сырая дельта очень большая, итог не выйдет за эти пределы.

### Пример “стабилизации”

- Сырая дельта до scale: `3000`
- После `delta_scale 0.02`: `60`
- Каппинг не срабатывает (60 < 180), итог `+60`.

Если бы после scale было `+240`, итог обрежется до `+180`.

## 5. Временные рамки (`T_ref`) по типам заданий

`T_ref` задается по группам:


| Номера                        | `T_ref`  |
| ----------------------------- | -------- |
| 1, 2, 3, 4, 10, 11            | 240 сек  |
| 5, 6, 7, 8, 12, 14, 16, 22    | 420 сек  |
| 9, 13, 15, 17, 19, 20, 21, 23 | 720 сек  |
| 24, 25                        | 1200 сек |
| 26, 27                        | 2100 сек |
| fallback                      | 420 сек  |

## 6. Где именно система должна работать

Проверяйте начисление/сохранение в сценариях:

- тренажер;
- сдача конкретного задания в работе (`submit-task`);
- финальная сдача работы;
- оценивание преподавателем (где запускается analytics).

В каждом из этих сценариев должен появляться `AnalyticsEvent`.

---

## 7. Что видеть в UI как тестировщик

## 7.1 У ученика / в интерфейсе сдачи

- тост после поштучной сдачи:
  - сложность
  - `ΔMMR`
- при корректной работе: не `—`, а конкретные значения.

## 7.2 В аналитике ученика

- история изменений рейтинга:
  - новое событие после каждой проверенной попытки;
  - столбцы/поля заполняются (в зависимости от роли).

## 7.3 У преподавателя

- расширенная история + коэффициенты;
- таблица рейтингов по узлам с колонкой калибровки;
- кнопка “Чистая” (reset solved_count по типу, без отката MMR).

---

## 8. Проверка “с нуля”: пошаговый smoke-plan

## 8.1 Базовый сценарий поштучной сдачи

- Открыть работу ученика, где доступна сдача по заданиям.
- Сдать 1 задание верно.
- Убедиться, что тост показывает `ΔMMR` и сложность (не `—`).
- Открыть аналитику ученика, проверить появление строки в истории.

## 8.2 Проверка влияния попытки

- На другом задании ответить неверно.
- Повторно ответить верно со 2-й попытки.
- Сравнить дельты: на 2-й попытке награда должна быть меньше (из-за `C_attempt=0.5`).

## 8.3 Проверка времени

- На номере с известным `T_ref` решить быстро/нормально/медленно.
- Проверить смену `time_band` и адекватность дельты.

## 8.4 Проверка калибровки

- На одном и том же номере выполнить серию решений.
- Проверить переход множителя: `x3 -> x2 -> x1`.

## 8.5 Проверка “Чистой калибровки”

- У преподавателя нажать “Чистая” для конкретного номера.
- Убедиться:
  - `calibration_remaining` сброшен к начальному;
  - текущий MMR не откатился.

## 9. Диагностика типовых проблем

## Проблема: тост показывает `ΔMMR —`

Возможные причины:

- analytics блок упал внутри `try/except`;
- событие не создалось;
- `rating_meta` вернулся `None`.

Что проверить:

- HTTP `POST /submissions/<id>/submit-task` = 200
- после этого есть запись в `AnalyticsEvent` по `submission_id/task_id`
- в ответе API есть `rating_meta.mmr_delta`.

## Проблема: событие не попало в историю

Что проверить:

- событие реально записано в БД;
- `GET /api/analytics/history` для правильного `student_id`;
- права доступа на просмотр.

## Проблема: “стандарт дал больше, чем хард”

Это может быть валидно, если:

- у стандарта выше калибровочный множитель (`c=2/3`),
- у харда уже `c=1`,
- и/или различаются время/попытка.

---

## 10. Референсные endpoint’ы для QA

- `POST /submissions/<submission_id>/submit-task`
- `GET /api/analytics/summary?student_id=<id>`
- `GET /api/analytics/history?student_id=<id>`
- `POST /api/analytics/calibration/reset`

---

## 11. Короткий итог для QA

Система считается рабочей, если:

- каждое проверенное действие создает событие в истории;
- `ΔMMR` стабильно считается (без `—`);
- коэффициенты объясняют разницу дельт;
- калибровка и ее ручной reset работают предсказуемо;
- нет экстремальных скачков из-за scale/cap защиты.
