## 3. Аудит 10 критических зон и закрытие P0/P1 дефектов

### 3.1 Кнопка «Повторить отправку» в кабинете Администратора (P0/P1)
**Выявленный риск:** Первоначальный сброс в `pending` не проверял актуальность урока, отзыв семейных связей, отписку пользователя или уже совершённую успешную отправку.  
**Решение:** Функция `retry_admin_delivery` в `app/telegram/v3/screens/admin.py` дополнена строгим каскадом проверок:
1. Запрет повтора для уже доставленных (`sent`, `simulated`) и находящихся в обработке (`processing`) сообщений.
2. Проверка статуса пользователя (`is_active`). При неактивном аккаунте доставка аннулируется (`cancelled: recipient account inactive`).
3. Проверка привязки Telegram. Если аккаунт отвязан — статус переводится в `cancelled: telegram identity unlinked`.
4. Проверка персональных настроек `UserNotificationPreference`. Если уведомление отключено — отмена с предупреждением администратору.
5. **Freshness Guard & TTL:** Проверка отмены урока (`lesson_cancelled`), начала урока в прошлом (`lesson_already_started`), проверки домашней работы (`submission_already_graded`), отзыва семейной связи (`family tie unconfirmed or revoked`) и срока давности > 48 часов (`expired_by_policy`).
6. **Идемпотентность:** Проверка отсутствия дублирующих успешных отправок по связанным `notification_id` / `lesson_id`.

### 3.2 Генерация внешних веб-ссылок вне HTTP-контекста (P1)
**Выявленный риск:** При вызове `deep_links._build` из фонового процесса бота или Celery вызов `url_for(..., _external=True)` завершался `RuntimeError` (отсутствовал URL-адаптер приложения без запроса), что приводило к генерации `None` вместо кнопок перехода на сайт.  
**Решение:** В `app/telegram/deep_links.py` внедрён надёжный fallback: при отсутствии адаптера запроса URL строится на основе базового публичного адреса `APP_URL` и канонической таблицы маршрутов BooStudy. Для пользователей в РФ ссылки формируют доступный адрес без VPN.

### 3.3 Обработка ошибок Telegram API: 403 (блокировка), 400, 429 (Rate Limit) (P1)
**Выявленный риск:** Низкоуровневый модуль `_tg_post` на ошибках `urllib.error.HTTPError` возвращал `None`, теряя JSON-ответ Telegram с кодом ошибки и описанием. Это приводило к тому, что 429 Rate Limit ошибочно помечался как фатальный сбой без ретрая, а 403 Forbidden не сохранял причину блокировки.  
**Решение:** В `app/telegram/notifications.py` добавлен парсинг тела `HTTPError`. В `app/telegram/delivery.py` при 403 («bot was blocked by the user») фиксируется предупреждение в логе и автоматически сбрасывается флаг `telegram_notifications_enabled = False` в профиле пользователя, предотвращая накопление бесполезных очередей. При 429 и 5xx активируется отложенный повтор по шкале `RETRY_DELAYS`.

### 3.4 Freshness Guard для запланированных уроков и TTL (P1)
**Выявленный риск:** `validate_delivery_freshness` проверял прошедшее время только для напоминаний `lesson_reminder`, но не для `lesson_scheduled`/`lesson_rescheduled`. Если урок уже прошёл, запоздалое сообщение о его создании всё равно отправлялось.  
**Решение:** В `app/telegram/delivery.py` добавлена проверка `now > lesson_date` для всех типов уроков, а также общий 48-часовой TTL для всех транзиторных уведомлений.

### 3.5 Аварийный выключатель Outbox (Emergency Kill Switch) (P1)
**Выявленный риск:** В случае непредвиденных внешних сбоев отсутствовал быстрый способ остановить все исходящие отправки без падения бота.  
**Решение:** В `is_delivery_permitted` в `app/telegram/config.py` добавлена проверка переменных `TELEGRAM_KILL_SWITCH=1` и `TELEGRAM_OUTBOX_PAUSED=1`. При их установке отправка сообщений мгновенно подавляется с фиксацией в аудите.

## 5. Эксплуатационная диагностика и операторский чек-лист

Для мгновенной проверки состояния экосистемы без раскрытия секретов подготовлен скрипт `scripts/check_telegram_status.py`.

**Запуск диагностики:**
```bash
./venv/bin/python scripts/check_telegram_status.py
```
**Пример вывода:**
```json
{
  "token_source": "TELEGRAM_DEV_BOT_TOKEN",
  "is_dev_token": true,
  "masked_token": "8784188271:***",
  "bot": {
    "id": 8784188271,
    "username": "BooStudy_local_bot",
    "first_name": "BooStudy_local",
    "can_join_groups": true
  },
  "bot_process_running": true,
  "conflict_detected": false,
  "outbox_stats": {
    "sent": 36,
    "simulated": 8,
    "cancelled": 176
  },
  "campaign_stats": {
    "completed": 1
  },
  "backend_running": true
}
```

### Чек-лист действий оператора при инцидентах:
1. **Конфликт polling (HTTP 409):**  
   Запустить `scripts/check_telegram_status.py`. Если `conflict_detected: true`, найти и завершить старый процесс `pgrep -f run_bot.py` или снять вебхук.
2. **Аварийная остановка исходящих сообщений:**  
   Выставить в `.env` переменную `TELEGRAM_KILL_SWITCH=1` — воркеры немедленно остановят отправку без перезапуска сервиса.
3. **Зависшие задания Outbox:**  
   Функция `recover_stale_processing(timeout_minutes=10)` автоматически возвращает зависшие задачи в статус `retry`.
4. **Откат на версию Bot V2:**  
   Установить `TELEGRAM_BOT_VERSION=v2` и перезапустить процесс `run_bot.py`.

## 7. Безопасный план развёртывания в Production

> [!IMPORTANT]
> Развёртывание в Production выполняется строго после отдельного подтверждения владельца платформы.

### Необходимые переменные окружения для Production:
```env
ENVIRONMENT=production
APP_URL=https://boostudy.ru
TELEGRAM_BOT_USERNAME=BooStudyBot
TELEGRAM_BOT_TOKEN=<PROD_BOT_TOKEN>
BOT_INTERNAL_TOKEN=<SECURE_INTERNAL_TOKEN>
TELEGRAM_BOT_VERSION=v3
TELEGRAM_MINI_APP_ENABLED=0
TELEGRAM_KILL_SWITCH=0
```

### Порядок включения:
1. Применить миграции базы данных PostgreSQL: `./venv/bin/python -m app.utils.db_migrations`.
2. Запустить фоновые воркеры Celery (`celery worker` и `celery beat`).
3. Запустить единственный процесс бота `python run_bot.py` через systemd/supervisor.
4. Проверить статус через `python scripts/check_telegram_status.py`.
5. Провести контрольную проверку 3 сценариев с аккаунта Создателя.
