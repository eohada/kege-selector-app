# 0. ГЛАВНОЕ ПРАВИЛО: MINIMAL CONTEXT

Контекст и токены — ограниченный ресурс.

Для обычных задач запрещено начинать работу с изучения всего проекта.

Стандартный алгоритм:

USER REQUEST
→ определить минимальный набор файлов
→ точечно найти нужный код
→ прочитать только необходимый фрагмент
→ внести правку
→ проверить diff / изменённый участок
→ STOP

Цель агента:

**правильная правка с минимальным количеством чтений**,  
а не максимальное понимание всего репозитория.

---

# 1. ЖЁСТКИЕ ОГРАНИЧЕНИЯ НА ИССЛЕДОВАНИЕ

Для обычной локальной задачи до первой правки:

- максимум 5 исходных файлов;
- максимум 2 поиска по проекту;
- максимум 3 исследовательских terminal-команды;
- один большой файл нельзя читать десятками отдельных диапазонов.

Если пользователь указал конкретные файлы — начать только с них.

Например, если задача касается:

- `task_workspace.html`
- `task_workspace.css`

не открывать другие исходники без конкретной необходимости.

Если кажется, что нужен дополнительный файл, сначала убедиться, что без него действительно невозможно выполнить задачу.

Не исследовать дополнительные файлы «на всякий случай».

---

# 2. БОЛЬШИЕ ФАЙЛЫ

Запрещено восстанавливать содержимое большого файла последовательным чтением множества кусков.

Плохой паттерн:

- lines 10–30
- lines 30–60
- lines 120–140
- lines 180–250
- lines 350–375
- lines 520–535
- и т.д.

Правильный паттерн:

1. Найти точный:
   - selector;
   - class;
   - id;
   - function;
   - component;
   - route;
   - видимый текст;
   - data-attribute.
2. Прочитать небольшой окружающий диапазон.
3. При необходимости прочитать ещё 1–2 связанных диапазона.
4. Внести изменение.

Не перечитывать уже просмотренные неизменённые участки без причины.

---

# 3. ЗАПРЕТ НА CODEBASE RESEARCH ПО УМОЛЧАНИЮ

Для локальных задач не нужно:

- сканировать repository;
- рекурсивно обходить директории;
- изучать архитектуру проекта заново;
- читать десятки похожих компонентов;
- искать «как это сделано везде»;
- запускать research/exploration subagent;
- смотреть git history без необходимости;
- читать документацию, не относящуюся к задаче.

Repository-wide investigation допустим только когда:

1. местонахождение реализации неизвестно;
2. ожидаемый файл не содержит нужной реализации;
3. меняется публичная сигнатура / модель БД / общий контракт;
4. задача действительно архитектурная или cross-cutting;
5. без дополнительного поиска невозможно сделать корректную правку.

Даже тогда искать конкретные символы, а не читать файлы подряд.

# 6. РАБОЧИЙ ПРОЦЕСС

Для обычной задачи:

1. Кратко понять задачу.
2. Определить минимальный набор файлов.
3. Точечно найти нужный участок.
4. Внести изменения.
5. Проверить изменённый участок и связанные с ним очевидные зависимости.
6. Остановиться.

Не нужно перед каждой задачей отдельно исследовать проект.

Не нужно писать длинный предварительный анализ.

Не нужно продолжать поиск после того, как место и способ исправления уже понятны.

# 7. КАЧЕСТВО КОДА

## NO LAZY CODING

Запрещены:

```text
// ... existing code ...
// TODO: implement later

Не оставлять незавершённую реализацию.

Не обрывать изменение на середине.

Редактирование файлов

Не создавать одноразовые Python-скрипты для редактирования файлов проекта:

rewrite_html.py
fix_profile.py
и аналоги.

Использовать встроенные инструменты редактирования агента.

Проверка

Перед завершением проверить:

синтаксис;
импорты;
закрытие скобок/тегов;
очевидные обращения к изменённому API;
diff изменённых файлов.

Не запускать широкую проверку всего проекта без необходимости.

8. IMPACT ANALYSIS

Impact analysis должен быть пропорционален изменению.

Для локальной HTML/CSS/UI-правки:

не искать все упоминания по всему проекту;
проверять только непосредственно связанные элементы.

Для изменения:

функции с внешними вызовами;
shared component;
API-контракта;
модели БД;
схемы;
route;
публичной сигнатуры;

разрешён targeted search всех использований изменяемого символа.

Не превращать impact analysis в общий аудит репозитория.

Формат сообщения:

12. PRODUCTION DEPLOY

Deploy production выполнять через blue-green.

cd /opt/boostudy
scripts/deploy_blue_green.sh deploy

Не рестартить web_prod напрямую.

Перед переключением трафика должен быть HTTP 200 от:

/ready

/ready проверяет:

PostgreSQL;
Redis;
миграции;
Socket.IO.

Миграции до switch должны быть backward-compatible / expand-only.

Предыдущий web-service не выключать сразу после переключения.

Safety window:

10–15 минут

Rollback:

cd /opt/boostudy
scripts/deploy_blue_green.sh rollback

PostgreSQL — источник пользовательского состояния.

Redis — кэш / snapshots.

Эти правила читать и применять только при задачах, связанных с production/deploy.

13. CHANGELOG И OBSIDIAN
Главное

CHANGELOG и Obsidian не являются обязательным этапом исследования перед каждой coding-задачей.

По умолчанию НЕ читать перед началом задачи:

CHANGELOG.md
Задачи/Список_задач.md
Задачи/Текущая_работа.md
Задачи/Лог_сессий.md

если пользовательская задача не требует информации из них.

Не использовать их для восстановления контекста локальной правки.

Когда читать

Читать CHANGELOG / Obsidian только если:

пользователь прямо просит работать с задачей из Todo;
требуется восстановить историю изменения;
требуется продолжить предыдущую незавершённую работу;
задача зависит от ранее принятого решения;
пользователь прямо просит обновить документацию/историю.
Когда обновлять

Не обновлять CHANGELOG и Obsidian после каждой мелкой технической операции.

Если ведение истории необходимо, делать запись один раз после завершения задачи, а не до и после каждого шага.

Не создавать пошаговый журнал каждой операции агента.

Не открывать CHANGELOG только ради добавления записи к простой локальной UI-правке, если пользователь этого не просил.

После этого:

EDIT → VERIFY CHANGED AREA → STOP

Не собирать дополнительный контекст просто потому, что он доступен.

QUICK REMINDER

Он действительно нужен для текущей задачи?

Можно ли найти точный symbol вместо чтения файла?
Я уже читал этот участок?

Если информации достаточно:
