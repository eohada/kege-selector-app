# BooStudy Theory — техническая спецификация авторинга

Дата исследования: 2026-11-09. Режим: read-only. Проверялись код приложения, шаблоны, стили, клиентский JavaScript, пакетные исходники теории и локальная SQLite в режиме `mode=ro`/`query_only=ON`. Приложение, БД и исходные материалы не изменялись; тесты не запускались.

## 1. Краткая карта архитектуры

| Назначение | Реализация |
|---|---|
| ORM-модели курса и материалов | `core/db_models.py`: `Course`, `TheoryGroup`, `TheoryBlock` и модели доступа/состояния |
| Маршруты каталога, статьи, управления и API | `app/theory/routes.py`, blueprint `theory_bp` |
| Сборка каталога и последовательное открытие | `app/theory/experience.py::build_experience` |
| Серверный разбор `TheoryBlock.content` | `app/theory/routes.py::_render_theory_content_html` и вызываемые им функции |
| Вывод статьи и клиентское поведение | `templates/sandbox/theory_article.html`; теория подключает связанные файлы из `static/` |
| Каталог и админ-раздел | `templates/sandbox/theory_experience.html`, `templates/sandbox/theory_admin_hub.html` |
| Импорт пакетного курса | `app/theory/curriculum.py`; CLI `scripts/import_theory_curriculum.py` |
| Примеры длинного контента | `scripts/python_theory_content_p1.py`, `scripts/python_theory_content_p2.py` |
| Тестовые примеры интерактивных маркеров | `tests/v2/test_theory_curriculum_package_v2.py` |

Основной путь ученика: `/theory` строит каталог; `/theory/topic/<block_id>` загружает материал и вызывает серверный рендерер; шаблон выводит сформированный HTML через `|safe`. Старый `/theory/<task_number>` перенаправляет на актуальный маршрут. Управление доступно через `/theory/manage` и API `/theory/api/manage/...`.

Рендерер — гибрид: сначала он извлекает собственные маркеры (`LEVEL`, `CHECKPOINT`, `INTERACTIVE`, карточки и т. п.), затем передаёт обычный Markdown расширениям Python-Markdown (`extra`, `tables`, `fenced_code`), после чего дорабатывает HTML через BeautifulSoup: форматирует код, изображения, заголовки и секции. Это не единый расширяемый Markdown-диалект и не полноценный Markdown AST-процессор. Порядок преобразований влияет на доступные возможности вложенности.

Важная особенность: `/theory/manage` при отсутствии групп может вызвать `_ensure_default_group` и записать «Общую группу» в БД. Это GET-страница с побочным эффектом. В рамках аудита маршрут не открывался и побочный эффект не вызывался.

## 2. Модель данных курса

### `Course` — `ExamCourses`

- `id`: первичный ключ.
- `title`: `String(200)`, обязательно.
- `slug`: `String(50)`, обязательно, уникальный индекс.
- `is_active`: Boolean, обязательно, default `true`.
- `created_at`: timestamp.

API создания: `api_manage_course_save` (`/theory/api/manage/course/save`). Требуется `title`; `slug` можно передать явно. Если его не передать, slug генерируется из заголовка, но заголовок на кириллице может свестись к общему `course-<timestamp>`. Для 15 курсов лучше передавать стабильный латинский slug. `is_active` по умолчанию включён.

### `TheoryGroup` — `TheoryGroups`

- `id`;
- `course_id`: nullable FK на курс, индекс, cascade delete;
- `name`: `String(200)`, обязательно;
- `description`: `String(500)`;
- `position`: Integer, обязательно, default `0`, индекс;
- `created_by`, `created_at`, `updated_at`.
- Уникальность `(course_id, name)`.

API: `api_manage_group_save` (`/theory/api/manage/group/save`). Принимает название, описание, позицию и курс; в отдельных ветках отсутствующий курс заменяется активным курсом по умолчанию. Автоматические позиции импортёра нумеруются от нуля; API управления может добавить группу после максимальной позиции.

### `TheoryBlock` — `TheoryBlocks`

- `id`;
- `course_id`: nullable FK на курс, индекс;
- `group_id`: nullable FK на группу, индекс; удаление группы оставляет материал без группы (`SET NULL`);
- `task_number`: Integer, обязательно, индекс;
- `title`: `String(200)`;
- `description`: `String(500)`;
- `read_minutes`: Integer, обязательно, default `5`;
- `position`: Integer, обязательно, default `0`, индекс;
- `content`: SQLAlchemy `Text`, nullable;
- `pdf_path`: `String(500)`;
- `created_at`, `updated_at`, `author_id`.
- Уникальность `(course_id, task_number)`.

Порядок в каталоге: курс — по `id`; группы — по `(position, id)`; материалы — по `(position, task_number, id)`. Поле `task_number` одновременно используется как номер материала/экзаменационная совместимость и участвует в ключах доступа, прогресса и попыток. Для курса из 174 статей нужны 174 уникальных `task_number` внутри курса. Стабильная последовательность `1…174` подходит структурно, но номер нельзя бездумно менять после выдачи материалов ученикам: данные доступа и прогресса адресуются этим номером.

`read_minutes` при API-сохранении приводится к диапазону 1–180; если пропущено, API управления использует default 15, хотя ORM default равен 5. Это оценка для интерфейса, не ограничение длины текста. Названия и описания ограничены 200/500 символами на уровне схемы.

### Состояние, доступ и блокировки

- `StudentCourseEnrollment`: уникальная пара студент/курс и флаг `is_active`. В API назначения (`/theory/api/manage/student/course-status`) представлены состояния `none` (нет записи), `assigned` (запись есть, `is_active=false`) и `active` (`true`). Каталог скрывает курс без назначения; назначенный, но неактивный курс не инициализируется как активный.
- `StudentTheoryAccess`: уникальная пара студент/курс/номер темы. Отсутствующая запись означает разрешение по умолчанию; явная `can_view=false` блокирует тему.
- `StudentTheoryState`: уникальная пара студент/курс/номер темы; хранит bookmark/read/progress/last_position/opened_at.
- `TheoryCheckpointAttempt`: уникальная запись студент/block/key; хранит последний ответ, корректность и счётчик попыток, а не полный журнал.
- `TheoryStudyAssignment`, обратная связь и история назначений — отдельные сущности; это не статусы публикации материала.

`experience.py::build_experience` строит последовательную блокировку каталога: следующая тема закрыта, пока предыдущая не завершена. Однако прямой маршрут статьи не применяет ту же проверку предшественников: `theory_view_block` проверяет публикацию, активность курса и явную блокировку преподавателя; при наличии записи enrollment учитывает её неактивное состояние, но отсутствие enrollment само по себе не является отказом в прямом запросе. Старый `_build_visible_with_state` содержит групповой вариант последовательной логики. Следовательно, последовательность — прежде всего UI/каталожное ограничение, а не надёжная серверная авторизация по всей цепочке.

### Черновик и публикация

Отдельного поля `status` у `TheoryBlock` нет. Статус хранится префиксом в `content`:

```html
<!--status:draft-->
```

или

```html
<!--status:published-->
```

`_with_status_prefix` записывает выбранный статус, `_extract_status` читает его. Контент без префикса считается опубликованным. Префикс удаляется перед рендерингом статьи. API `api_manage_block_save` принимает статус и при обновлении по `id` изменяет существующий материал. При создании повтор `task_number` для курса отклоняется.

### Ёмкость курса из 174 статей

На уровне ORM нет лимита числа курсов, групп или материалов и нет `VARCHAR`-ограничения на `content`: SQL-тип — `Text`. API статьи также не задаёт лимит тела. Настройка приложения `MAX_CONTENT_LENGTH=None`. Значит, 15 групп и 174 больших статьи допустимы без изменения схемы. Реальные пакетные материалы в исходниках достигают около 23 тыс. символов; подтверждённый единый верхний лимит платформы/веб-сервера/хранилища не найден — для очень больших файлов предел инфраструктуры **НЕ ПОДТВЕРЖДЁН**.

Локальная БД была прочитана в режиме read-only: в ней 6 курсов, но 0 строк в `TheoryGroups` и 0 строк в `TheoryBlocks`. Упоминания «реальных статей» ниже поэтому относятся к пакетным исходникам репозитория, а не к live-записям этой БД.

## 3. Полная спецификация `TheoryBlock.content`

### Подтверждённая базовая грамматика

Обычный текст обрабатывается Python-Markdown с расширениями `extra`, `tables`, `fenced_code`. Подтверждены заголовки `#`–`######`, абзацы, жирный/курсивный текст, inline-code, обычные и вложенные списки Markdown, нумерованные списки, Markdown-таблицы, blockquote, горизонтальный разделитель `---`, ссылки и fenced code. Рабочий рендерер расположен в `app/theory/routes.py::_render_theory_content_html`; зависимости объявлены в `requirements.txt`.

Пример стандартного Markdown:

```markdown
## Делимость

Число **делится** на 3, если сумма его цифр делится на 3.

1. Найдите сумму цифр.
2. Проверьте её делимость на 3.

- Для 123 сумма равна 6.
  - 6 делится на 3.

| Число | Сумма цифр | Делится на 3 |
|---:|---:|:---:|
| 123 | 6 | Да |

> Проверка делимости сокращает вычисления.

---

[Правило делимости](https://example.org)
```

Результат: `##` становится секцией статьи с оформленной карточкой и пунктом оглавления; список и вложенный список становятся HTML-списками; таблица — таблицей; цитата — `<blockquote>`; `---` — `<hr>`; ссылка — обычной HTML-ссылкой. Оформление определяется CSS статьи, а не дополнительным синтаксисом.

Ограничения/ошибки: пустая строка важна для разделения Markdown-блоков. Для таблиц используйте стандартный синтаксис с разделительной строкой. Внутри пользовательских маркеров доступный Markdown иной и ограничен (см. разделы ниже). Не используйте одинокие pipe-таблицы с формулами без проверки: их альтернативный путь преобразования экранирует содержимое ячеек.

### Заголовки и секции

Допустимы стандартные уровни Markdown `#`–`######`. `##` имеет специальное значение: формирует тематический раздел, карточку и элемент TOC; классификация секции зависит от текста заголовка. Первый `h1` может стать названием/верхней шапкой в зависимости от шаблона, поэтому не дублируйте им название статьи без причины. В админ-шаблоне встречается подсказка `[section:...]`, но в серверном парсере такого маркера нет; используйте `## Название`, а не `[section:...]`.

Основные автоматические категории `##` (правила по совпадению заголовка в `_render_theory_content_html`): «Что проверяет экзамен»/«Зачем это нужно в ЕГЭ» → цель; «Теория» → концепция; заголовок с «алгоритм»/«шаги» → метод; «практика»/«примеры»/«лаборатория» → практика; «ошибки»/«ловушки» → предупреждение; «микро-проверки» → проверка; «итог темы» → итоговая секция. Неизвестный заголовок получает базовую секционную карточку. Не рассчитывайте на отдельную специальную цветовую тему для каждого произвольного заголовка.

### Списки, таблицы, цитаты, разделитель, ссылки

Поддержка наследуется от Python-Markdown `extra`/`tables`: стандартные `- пункт`, `1. пункт`, вложение отступом, `> цитата`, `---` и `[текст](https://...)`. Собственный нормализатор также распознаёт некоторые текстовые списки/шаги, но автору следует предпочитать канонический Markdown. Стандартные таблицы поддерживаются. В некоторых простых ASCII-таблицах строка с pipe может быть преобразована отдельным парсером; ячейки там безопасно экранируются, поэтому встроенный HTML/сложная разметка в них не является надёжной возможностью.

Внутренние ссылки должны быть обычными URL или Markdown-ссылками. Автоматической валидации URL/наличия страницы нет. Поведение внешних ссылок при открытии в новой вкладке не следует считать контрактом автора.

### HTML и безопасность

Сырой HTML пропускается Python-Markdown и в теоретическом маршруте не проходит allowlist-фильтр. Итоговый результат передаётся шаблону как безопасный HTML (`Markup`/`|safe`). Зависимость Bleach в проекте не означает, что теория санитизируется: в пути `_render_theory_content_html` вызова Bleach не обнаружено. Поэтому HTML-теги в контенте могут попасть в страницу. Это технически означает, что HTML разрешён, но для доверенного авторского курса контракт должен запрещать сырой HTML, `<script>`, обработчики событий, iframe и внешние встраивания. Не передавайте пользовательский недоверенный текст как авторский контент.

### Переносы и спецсимволы

Содержание передаётся как Unicode-текст в SQL `Text`, без JSON-экранирования после корректного декодирования. Обычные переводы строк нормализуются рендерером и Markdown-правилами; для отдельных блоков оставляйте пустые строки и не полагайтесь на каждый одиночный перевод как на `<br>`. Внутри `[CODE]` содержимое специально защищается от Markdown/math-прохода и экранируется как код. В API атрибуты маркеров парсятся в кавычках, поэтому кавычки и обратные слеши в атрибутах нужно корректно JSON-экранировать при импорте и не вставлять сырой перевод строки в атрибут.

### Форматы, которых нет в базовом Markdown-контракте

- Markdown-спойлеры/HTML `<details>` как специальная поддерживаемая функция — **НЕ ПОДТВЕРЖДЕНО**; сырой HTML может пройти, но стандартного дизайна/прогресса для раскрытия нет.
- Mermaid, LaTeX-рендерер, диаграммы, SVG-графы по текстовой грамматике — не обнаружены.
- `[section:...]` — не поддерживается, несмотря на подсказку в админ-шаблоне.
- `[GHOST_IMAGE ...]` удаляется и не выводит изображение.

## 4. Математический рендеринг

В `templates/sandbox/theory_article.html` не подключён KaTeX/MathJax. В других, не относящихся к статье шаблонах проекта встречается KaTeX, но это не подтверждает рендеринг теоретических материалов. Реализована собственная ограниченная строковая функция `_format_inline_math_html` в `app/theory/routes.py`.

### Подтверждённый синтаксис

- Inline: `$...$`.
- Отдельное отображаемое выражение: `$$...$$`.
- Простая дробная черта через обычный `/`, например `$a/b$`; это текстовая запись, а не команда `\frac`.
- Простые `\sqrt{...}` без вложенных фигурных скобок.
- Простой индекс и степень `_`/`^` с короткой группой/символом.
- Команды `\text{}`, `\mathbf{}`, `\mathit{}` в ограниченной простой форме.
- Преобразуются команды пробела `\quad`, `\,`, `\;`, `\!`, операторы `\cdot`, `\times`, `\ge`, `\le`, `\ne`, `\to`, `\equiv`, логические `\land`, `\lor`, `\neg`.

Рабочий небольшой пример:

```markdown
Если $a>0$, то $\sqrt{a^2}=a$.

$$x^2+1=0$$
```

Это будет выведено как ограниченное inline/display-подобное оформление строки с символами superscript/subscript и подстановкой распознанных команд, а не как полноценная типографская формула TeX.

### Не подтверждено/не поддержано

Команды `\frac`, `\dfrac`, `\tfrac`, `\sum`, `\int`, `\lim`, `\begin{cases}`, `\begin{aligned}`, `\begin{matrix}`, `\left`, `\right`, большинство греческих букв и общая TeX-грамматика этим рендерером не реализованы. Вложенные группы формул не разбираются как TeX. Системы уравнений, случаи, пределы, суммы и интегралы нельзя считать поддержанными; экранированные команды останутся текстом/могут быть преобразованы некорректно. Символические конструкции не проходят компиляцию/валидацию.

В реальных пакетных материалах есть строки `$F(n) = F(n-1) + F(n-2)$`, `$N \\log N$`, `$\\approx$` и `$\\cdot$`. Присутствие `\\log` или `\\approx` в источнике не является доказательством их типографской поддержки; преобразуются только перечисленные выше команды.

### Вложенные блоки и адаптивность

Обычный текст, `LEVEL` и тела простых callout-блоков проходят ограниченный math-проход. Кодовые блоки исключены из него. Поля вопросов/ответов/options у `CHECKPOINT` и prompt/options у `INTERACTIVE` извлекаются раньше и выводятся отдельным путём; надёжный math-рендеринг в этих полях не подтверждён. В таблицах результат зависит от того, использовал ли контент стандартный Markdown или альтернативный pipe-parser; сложная формула в ячейке не гарантирована.

Для длинных формул нет подтверждённой обёртки с горизонтальной прокруткой: `.theory-inline-math` имеет `white-space: nowrap`. На узком экране длинная формула может выйти за ширину/обрезаться. Сохранение обратных слешей в `Text`/JSON возможно, но их отображение ограничено парсером, а не базой.

**Вывод для курса:** текущая математика пригодна для коротких школьных выражений из поддержанного подмножества; не готова для полноценной записи профильной математики. Не передавать в статьи общие TeX-формулы с ожиданием корректного отображения.

## 5. Визуальные блоки

Все перечисленные ниже маркеры разбираются серверной функцией `_render_theory_content_html` в `app/theory/routes.py`; внешний вид статьи и контролов задают `templates/sandbox/theory_article.html` и подключённые статические стили. Маркерные карточки преимущественно извлекаются до Markdown, поэтому не наследуют весь набор Markdown-возможностей.

| Тип | Точный синтаксис | Отображение и ограничения |
|---|---|---|
| Запомнить | `[REMEMBER]текст[/REMEMBER]` | Акцентная карточка-напоминание. В теле есть inline bold/italic/code и ограниченная математика; полноценная вложенная таблица/список не подтверждена. |
| Важно | `[IMPORTANT title="Заголовок"]текст[/IMPORTANT]` | Карточка важной мысли; `title` необязателен. |
| Примечание | `[NOTE title="Заголовок"]текст[/NOTE]` | Нейтральная информационная карточка; `title` необязателен. |
| Предупреждение | `[WARNING title="Заголовок"]текст[/WARNING]` | Предупреждающий стиль; `title` необязателен. |
| Совет | `[TIP title="Заголовок"]текст[/TIP]` | Подсказка/совет; `title` необязателен. |
| Информация | `[INFO title="Заголовок"]текст[/INFO]` | Информационный стиль; `title` необязателен. |
| Попробуйте | `[TRY title="Заголовок"]текст[/TRY]` | Карточка-приглашение к самостоятельному действию; `title` необязателен. |
| Как это работает | `[HOW_IT_WORKS speech="Короткая фраза"]текст[/HOW_IT_WORKS]` | Поясняющая карточка; `speech` необязателен. Если весь body состоит из нумерованных строк, отображается как последовательность шагов. |
| Универсальный callout | `[CALLOUT type="attention|warning|tip|info|danger"]текст[/CALLOUT]` | Карточка темы по `type`; неизвестное значение переходит в `info`. Заголовок отдельно не задаётся. |
| Типы данных | `[DATA_TYPES]` с дочерними `[TYPE name="..." label="..." desc="..." code="..."]` и `[/DATA_TYPES]` | Специализированная сетка элементов; формат дочернего TYPE — атрибутный, не произвольный текстовый блок. |
| Операции | `[OPERATIONS]` с дочерними `[OP sign="..." name="..." example="..." result="..." note="..."]` и `[/OPERATIONS]` | Табличная/карточная визуализация операций; каждый OP задаётся атрибутами. |
| Практическое задание | `[PRACTICE_TASK id="..."]текст[/PRACTICE_TASK]` | Оформленная карточка задания; содержимое не является CHECKPOINT и само не проверяется сервером. |
| Заголовок-секция | `## Название` | Карточка раздела и TOC; цвет/семантика выбираются по ключевым словам заголовка (раздел 3). |

Примеры реального синтаксиса:

```text
[REMEMBER]
Знак `=` в программировании означает **присваивание**, а не равенство!
[/REMEMBER]

[IMPORTANT title="Проверка"]
Подставьте найденное значение обратно в исходное условие.
[/IMPORTANT]

[CALLOUT type="warning"]
Не сокращайте дробь на выражение, которое может быть равно нулю.
[/CALLOUT]

[HOW_IT_WORKS speech="Разница между /, // и %"]
1. Обычное деление `/` всегда делает число вещественным.
2. Деление `//` оставляет целую часть.
3. Оператор `%` возвращает остаток.
[/HOW_IT_WORKS]

[PRACTICE_TASK id="divisibility-1"]
Проверьте делимость 123 на 3 по сумме цифр.
[/PRACTICE_TASK]
```

Для `DATA_TYPES` и `OPERATIONS` рабочие полные примеры есть в разделе 11. Атрибутные типы сами по себе не эквивалентны произвольным вложенным блокам: не помещайте в `desc`, `code`, `note` сложную разметку с кавычками и переводами строк без экранирования. `TYPE code` хранит переводы строк через `\n` в атрибуте.

### Кодовые блоки и подсветка

Обычный Markdown fenced code поддержан:

````markdown
```python
print(2 + 2)
```
````

Он превращается в карточку `.theory-code-snippet` с кнопкой копирования; для Python применяется Pygments-подсветка, если библиотека доступна. Отдельный авторский синтаксис:

```text
[CODE lang="python"]
print(2 + 2)
[/CODE]
```

`[CODE]` формирует кодовую карточку; Python подсвечивается при доступном Pygments, прочие языки экранируются без подтверждённой подсветки. Внутри содержимое экранируется и защищено от Markdown и математической подстановки. Для исполняемого редактора существует `[CODE_RUNNER title="..." input="..." output="..."]...[/CODE_RUNNER]`: сервер умеет исполнять только Python с timeout 3 с; `output` — показываемый ожидаемый вывод, не полноценная проверка корректности математического ответа. Не использовать для недоверенного/тяжёлого кода.

Маркер `[GHOST_IMAGE ...]` удаляется рендерером, изображения так не добавлять.

Существуют ли отдельные компоненты определения, теоремы, скрываемого ответа, раскрывающегося объяснения, списка ошибок или итогов с уникальным маркером — не подтверждено. Для них используйте базовые карточки `[IMPORTANT]`, `[NOTE]`, `[WARNING]`, `[TIP]` либо заголовок `## Итог темы`; не выдумывайте маркеры `[THEOREM]`, `[DEFINITION]`, `[SOLUTION]`, `[DETAILS]` и т. п. Обычная Markdown-цитата стилизуется как blockquote, но не является отдельной теоремой.

## 6. `LEVEL` — варианты уровня подачи

### Синтаксис и фактическое поведение

```text
[LEVEL name="beginner" label="Базовый"]
Содержание варианта.
[/LEVEL]
```

`name` обязателен и произволен; `label` необязателен. Подтверждены несколько соседних `LEVEL` в одной статье. Каждый уровень рекурсивно прогоняется тем же Markdown/custom renderer, поэтому внутри работают обычные Markdown-конструкции, разрешённые маркеры, а также ограниченный math-проход. `LEVEL` внутри `LEVEL` не поддержан надёжно: парсер ориентирован на плоские блоки одного имени и вложенное использование не является контрактом.

Три рабочих примера синтаксиса:

```text
[LEVEL name="basic" label="Базовый"]
Число делится на 2, если последняя цифра чётная.
[/LEVEL]
```

```text
[LEVEL name="standard" label="Стандартный"]
Для числа $10a+b$ делимость на 2 определяется значением $b$.

1. Найдите последнюю цифру.
2. Проверьте, чётная ли она.
[/LEVEL]
```

```text
[LEVEL name="advanced" label="Углублённый"]
| Остаток последней цифры | Вывод |
|---:|---|
| 0, 2, 4, 6, 8 | Число делится на 2 |

[CHECKPOINT key="level-parity" question="Делится ли 128 на 2?" options="Да|Нет" answer="Да"]
[/LEVEL]
```

Примеры демонстрируют маркерную грамматику; пример с checkpoint использует плоский уровень, но вопрос внутри него получает те же ограничения, что CHECKPOINT везде (формула в вопросе не гарантирована).

### Переключение — существенное ограничение

Рендерер оборачивает первый `LEVEL` активным, остальные скрытыми; выбранное значение сохраняется в `localStorage` под ключом `boostudy_theory_level`. В `theory_article.html` и связанном клиентском коде не обнаружена генерация/разметка ожидаемых JS-селекторов `#theory-level-switcher`, `#mobile`/`.theory-level-tab` (данные об уровне в HTML есть, но штатного переключателя нет). Поэтому нельзя рассчитывать, что ученик сможет сменить уровень: последующие панели могут оставаться скрытыми. Если в статье есть один `LEVEL`, wrapper без переключателя также не даёт преимуществ.

`LEVEL` не задаёт права доступа и не является прогрессом/отдельным назначением. Прогресс чтения относится к статье целиком. CHECKPOINT внутри имеет собственную запись попытки по ключу; ключи повторять между уровнями нельзя, иначе они конфликтуют на уровне `(student, block, key)`. Текст вне распознанных обёрток при обнаружении LEVEL может не попасть в ожидаемое место, поэтому не смешивайте свободный текст до/после вариантов. До появления/проверки переключателя для авторского пакета: **не использовать несколько уровней в публикуемых статьях**; если уровни требуются — содержание доступно только при наличии подтверждённого переключателя в конкретной сборке.

## 7. `CHECKPOINT` — встроенная проверка

### Подтверждённая грамматика: только одиночный выбор

```text
[CHECKPOINT key="уникальный-ключ" question="Вопрос" options="Вариант 1|Вариант 2|Вариант 3" answer="Вариант 2" explanation="Разбор правильного ответа." hint="Подсказка при ошибке"]
```

Обязательное содержимое: непустой `question`, не менее двух `options`, `answer`, который в точности совпадает с одним из вариантов. `key` необязателен; если не задан, генерируется `checkpoint-N`. Разделитель вариантов — `|`, поэтому сам вариант не должен содержать pipe. `explanation`/`hint` предусмотрены атрибутами. Никаких форматов numeric, multi-select, matching, ordering или true/false с отдельной логикой у CHECKPOINT не обнаружено: доступен ровно single-choice.

Реальный фрагмент из `scripts/python_theory_content_p1.py`:

```text
[CHECKPOINT key="calc-div-101" question="Чему равен результат выражения 17 // 5 в Python?" options="3.4|3|2|1" answer="3" explanation="Оператор // выполняет деление нацело: 17 // 5 = 3."]
```

### Проверка, повторные попытки и прогресс

Клиент отправляет выбранную строку; сервер сравнивает её с правильным ответом точным сравнением. Варианты перемешиваются детерминированно по ключу. Правильный ответ не выдаётся в HTML до отправки проверки. После неверного выбора UI позволяет повторить попытку; `hint` показывается при ошибке, `explanation` — при успехе. Восстановление сохранённой попытки использует общий/подсказочный текст, а не гарантирует прежнее подробное состояние.

`TheoryCheckpointAttempt` хранит последнюю попытку/ответ, её корректность и счётчик. Полной истории попыток нет. Отдельный checkpoint не является условием завершения статьи: чтение/progress статьи обновляется отдельно, а автоматическое `is_read` наступает примерно на 95% прогресса. Если ключ не задан, при перестановке/добавлении блоков автоключ может измениться. Для курса всегда задавайте стабильный уникальный `key`, не длиннее 80 символов по схеме. Длина `selected_answer` ограничена 500 символами.

### Числа и математика

Числового парсинга нет. `2`, `2.0`, `2,0`, `2/1` — разные строки. Нет нормализации десятичной запятой, отрицательных чисел, пробелов внутри ответа, допуска, сравнения дробей или проверки эквивалентности выражений. Допустимые варианты можно перечислить как отдельные варианты только в single-choice, но нельзя задавать несколько правильных вариантов. Поля вопроса/options проходят не тот math-проход, что основной текст статьи; формулы в них не следует использовать.

## 8. `INTERACTIVE` — интерактивные задания

### Общая грамматика

```text
[INTERACTIVE type="choice" key="unique-key" prompt="Выберите ответ" options="A|B|C" answer="B" hint="Подумайте о знаке" rows="2" code="print(2)" expected="2" placeholder="Введите ответ"]
```

Парсер признаёт атрибуты `type`, `key`, `prompt`, `answer`, `options`, `code`, `expected`, `placeholder`, `rows`, `hint`. `prompt` и непустой `answer` обязательны для всех типов, включая code/debug. `type` по умолчанию `input`; неизвестный тип пропускается. `key` желательно всегда задавать уникально и стабильно. `explanation` не входит в реально обработанные атрибуты. `rows` ограничен максимумом 8. `slider` фиксирован в диапазоне 0–100.

Распознанный перечень типов: `input`, `choice`, `order`, `table`, `code`, `boolean`, `multi`, `match`, `classify`, `fill`, `slider`, `hotspot`, `sequence`, `trace`, `regex`, `binary`, `formula`, `predict`, `debug`, `explain`. Перечень — названия типов UI, а не 20 независимых алгоритмов проверки: несколько типов используют общий exact-string fallback.

### Типы и формат ответа

| `type` | Разметка и взаимодействие | Проверка/ограничения |
|---|---|---|
| `input` | Текстовое поле, `prompt`, `answer`, необязательный `placeholder` | Точный строковый ответ после trim/lowercase; свободная форма не означает семантическую проверку. |
| `choice` | `options="A|B"` | Выбрать один вариант; точный ответ. |
| `multi` | `options="A|B|C"`, `answer="A|C"` | Несколько флажков; сравнение наборов, порядок ответа не важен, правильный набор должен совпасть. |
| `classify` | `options="..."` | UI выбора категорий/элементов, проверка множества как у multi. Не заменяет произвольную многоколонную классификацию. |
| `boolean` | `answer="true"` либо false-вариант | Истина принимается как `true`, `1`, `да`, `yes` после нормализации; остальное интерпретируется как false. |
| `order` | `options="a|b|c"`, ответ `a>b>c` | Собрать порядок кликами; последовательность сравнивается с ожидаемой. |
| `sequence` | Как order: `options`, ответ с `>` | Аналогичный порядок последовательности; отдельной пошаговой проверкой промежуточных шагов не является. |
| `table` | `rows="N"` (до 8), ответ `v1|v2|...` | Ввести значение для каждой строки; сравнение по соответствующим ячейкам/строкам. |
| `trace` | `rows="N"`, ответ `v1|v2|...` | Табличная трассировка, модель ответа такая же, как для нескольких строк. |
| `match` | Ввод пары, ответ `left=right` | Проверяется одна пара; стороны сравниваются нормализованно. Нет редактора произвольного множества пар. |
| `hotspot` | Выбор ячейки сетки | Фиксированная сетка 3×3, номера ячеек 1–9; правильный ответ — номер/набор ожидаемой клетки согласно компоненту. |
| `slider` | Ползунок 0–100 | Значение должно совпасть точно; диапазон и шаг нельзя задать в маркере. |
| `fill` | Поле пропуска | Общая точная строка; текстовый пропуск не понимает множество ответов. |
| `formula` | Поле формулы | Несмотря на имя, это не символьный математический компаратор: общий exact-string ответ. |
| `predict` | Поле прогноза | Общая точная строка. |
| `regex` | Поле текстового ответа | Имя типа не означает исполнение регулярного выражения на ответе; используется общий exact-string путь. |
| `binary` | Поле двоичного представления | Общая точная строка; преобразования из десятичного числа нет. |
| `explain` | Поле объяснения | Требует совпадения с заданной строкой, не оценивает смысл объяснения. |
| `code` | Python-редактор с атрибутами `code`, `expected` | Сервер запускает Python и сопоставляет stdout с `expected` (или заданным answer fallback) после trim; Python-only, timeout 3 секунды. |
| `debug` | Python-редактор | Та же серверная проверка кода; нет автоматической диагностики конкретной ошибки. |

В `match` проверяется одна пара, не полноценная задача на сопоставление. `order`/`sequence` — сбор последовательности из вариантов, а не объяснение каждого шага. Поэтапный фидбек, подсветка конкретного неверного элемента и разные сообщения для ошибок не поддержаны контрактом. `hint` для интерактивных маркеров парсером может сохраниться в модели, но текущий UI не показывает его как checkpoint-подсказку при ошибке; `explanation` игнорируется.

### Проверка, хранение и формулы

Клиент отправляет результат на серверный API проверки теории. Сервер повторно вычисляет корректность, не полагаясь на ответ клиента; для `code` используется серверный запуск Python с таймаутом около 3 секунд. Ответ/правильное значение не должны отдаваться заранее в клиентской разметке. Попытка сохраняется как последний ответ по уникальному `(student, block, key)` и увеличивает счётчик; жёсткий лимит числа попыток в проверенной схеме/обработчике не обнаружен. История ответов не хранится.

Математические ответы проверяются строково. Нет десятичного парсинга, запятой как десятичного разделителя, дробной эквивалентности, допуска, символьного упрощения, нормализации LaTeX или набора допустимых альтернатив. Поддержка отображения математических формул в `prompt`/вариантах также не подтверждена. В code можно выводить текст, но это интерактив Python, не математический движок.

Несколько интерактивных блоков в одной статье поддерживаются; это подтверждено тестом, который рендерит все форматы в одной статье. Всегда задавайте разные ключи: одинаковый ключ приводит к перезаписи состояния попытки. Вложить интерактивный маркер внутрь другого интерактивного блока или внутрь атрибута нельзя считать поддержанным. На мобильном используются штатные адаптивные классы, но целевых мобильных визуальных тестов для всех 20 режимов не обнаружено — адаптивность каждого режима **НЕ ПОДТВЕРЖДЕНА**.

## 9. Иллюстрации и геометрические чертежи

### Подтверждённые способы

Стандартное изображение Markdown:

```markdown
![Треугольник ABC с высотой](https://example.org/triangle.png)
```

Рендерер принимает `http://`, `https://`, protocol-relative URL, `data:`, `/static/...` и `/theory/uploads/...`. Для относительного имени файла с расширением изображения он пытается найти файл в каталогах загрузок теории и подменяет путь. Локальное найденное изображение выводится lazy и с inline адаптивными параметрами примерно `max-width:min(100%,920px); height:auto`; у удалённого URL такое локальное оформление не гарантировано. Голая строка с именем файла тоже может распознаться как картинка, но лучше использовать Markdown.

Маршрут `/theory/upload-image` требует входа и `_can_manage`; принимает multipart-файл PNG, JPG/JPEG, GIF, WebP, SVG; предел одного изображения — 15 МБ. Файлы хранятся в persistent `THEORY_UPLOAD_ROOT` или static uploads. API загрузки PDF имеет предел 30 МБ, общего файла — 40 МБ. Наличие действующего контрола загрузки именно в текущем `theory_admin_hub.html` не подтверждено поиском ссылки на endpoint; endpoint подтверждён. Без UI доступность загрузки через интерфейс преподавателя помечается **НЕ ПОДТВЕРЖДЕНО**.

Подписи отдельной конструкцией не поддерживаются. Размещайте изображение и следующий за ним отдельный абзац с подписью; специальная семантика `<figure>/<figcaption>` не подтверждена. Несколько изображений подряд через отдельные Markdown-строки допустимы. Вставка raw SVG/HTML может пройти как сырой HTML без санитизации — это небезопасный авторский формат; используйте отдельный SVG-файл, загруженный доверенным преподавателем, или PNG/WebP.

### Графики и геометрия

Не найдены встроенные координатные оси, plotter, диаграммы, Mermaid или автоматическое построение по функции. Практический совместимый способ — создать статический PNG/WebP (или доверенный загруженный SVG), сохранить через доступное хранилище `/theory/upload-image` и вставить Markdown-ссылкой с осмысленным alt-текстом; подпись оформить обычным абзацем. Такой путь опирается на существующую архитектуру, но создание/версионирование изображений пакетом не автоматизировано.

## 10. Сохранение, управление и загрузка статей

### Управление через `/theory/manage`

Маршрут показывает активные курсы, группы и материалы. Для списка админ-шаблон использует `_get_course_groups_with_blocks`; эта функция выбирает целые ORM-объекты `TheoryBlock`, включая большие bodies. Поэтому при 174 длинных статьях страница управления может загрузить весь объём текстов в память/HTML управления. Каталог для ученика оптимальнее: `experience.py::build_experience` выбирает метаданные, не `content`.

`/theory/manage` требует преподавательские права, но не следует открывать его при read-only-аудите: при отсутствии группы маршрут может создать дефолтную группу и сделать commit. Импорт и API можно использовать для работы только в согласованной среде и с проверенным аккаунтом.

### API сохранения

- Курс: `POST /theory/api/manage/course/save` (`api_manage_course_save`): обязательный `title`, опциональный `slug`, активность.
- Группа: `POST /theory/api/manage/group/save` (`api_manage_group_save`): курс, `name`, `description`, `position`.
- Материал: `POST /theory/api/manage/block/save` (`api_manage_block_save`): `title` обязательно; для детерминированного импорта передавать `course_id`, `group_id`, `task_number`, `description`, `read_minutes`, `content`, `status`; при редактировании передавать существующий `id`.

На создание `task_number` может вычисляться как следующий после максимального, но авторскому пакету лучше передавать явно. Дубликат уникальной пары course/task_number отклоняется. По `id` API обновляет текущую строку — это путь избежать дубликата при повторной доставке, но сначала нужно сверить, что `id` соответствует ожидаемому курсу и номеру. Публикация через статус реализуется content-префиксом. Можно передать `status="draft"`, сохранить и проверить как черновик; публикация — отдельный перевод статуса. Режим доступа к предпросмотру черновика нужно проверить в конкретной роли/сборке перед рабочим процессом.

### Авторизация и CSRF

Маршруты управления требуют входа и проверки прав преподавателя (в частности, `_can_manage`). В `app/__init__.py` весь `theory_bp` глобально исключён из Flask-WTF CSRF через `csrf.exempt(theory_bp)`, хотя UI отправляет CSRF-заголовки. Значит, нельзя утверждать, что API теории защищён CSRF-токеном; фактический контракт защиты — авторизационные проверки маршрута и ограничения контекста. Для будущего импорта запускать API только из доверенного авторизованного контекста; не встраивать токены в пакет статей и не обходить проверку роли.

### Есть ли Markdown-импорт

Отдельного универсального импорта `.md` не обнаружено. Markdown можно положить в `content` как строку через block-save API или специальный JSON импортёр. Markdown-файлы сами по себе не загружаются маршрутом управления.

`app/theory/curriculum.py::import_curriculum` умеет upsert курсов/групп/блоков из данных и сохраняет `content` без намеренной переписи статьи. Совпавший курс/slug и `task_number` обновляет существующую запись и сохраняет ID, что сохраняет внешние ссылки и состояние ученика. Отсутствующие во входном пакете записи не удаляются. Однако штатный путь `scripts/import_theory_curriculum.py` вызывает `load_curriculum`, который жёстко ориентирован на информатику: `schema_version=1`, минимум две группы, номера 1–27, минимум 1000 символов на статью и дополнение Python-лабораторией. `_add_topic_lab` модифицирует каждый блок; скрипт поэтому не подходит для прямой загрузки авторского курса математики как есть.

В репозитории есть статическая несогласованность импортёра: проверенные JSON-пакеты имеют одну группу, тогда как `validate_curriculum` требует минимум две; `_apply_intro_programming_lessons` меняет существующую группу, но не добавляет вторую. Также тест `test_ege_curriculum_is_complete_and_detailed` ожидает две группы. Следовательно штатная цепочка `load_curriculum` выглядит несовместимой со своим текущим исходным JSON по коду. Это вывод статического анализа; импортёр не запускался и БД не менялась.

### Безопасная схема будущего импорта

1. В отдельном ревью-пакете передавать manifest курса и статьи в UTF-8 JSON: `schema_version`, стабильный `slug`, группы с `key/name/position`, статьи с `task_number/group_key/position/title/description/read_minutes/status/content`.
2. Сначала валидировать пакет офлайн: уникальность slug/group key/task_number, соответствие 174 номеров, длины метаданных, уникальные маркерные ключи, валидность кавычек атрибутов, допустимость только подтверждённых конструкций. Контент не переписывать Markdown-конвертером.
3. До записи загрузить материал как draft; использовать существующий API save с явным `course_id`, `group_id`, `task_number`, затем повторно получить статью/preview от сервера и сравнить нормализованный UTF-8 текст/байтовый SHA-256 с исходным content без служебного status prefix.
4. Хранить в manifest выданные `block_id` и пару `(course slug, task_number)`. При повторе сначала искать эту пару и обновлять по существующему `id`; не создавать строку при неразрешённом конфликте. Текущий `import_curriculum` делает upsert по course/task_number, но его информатический CLI не использовать для математики без адаптации вне текущей задачи.
5. Публиковать после отдельной проверки рендеринга человеком; переводить существующие строки по ID/статусу. Не удалять отсутствующие статьи и не переназначать номера, иначе можно затронуть привязанные записи ученика.

Это рекомендация по интеграции, а не реализованный функционал пакетного JSON-валидатора/preview. Не выполнять импорт непосредственно сырыми массовыми API-запросами без manifest и сверки результата.

## 12. Технический контракт авторинга для ChatGPT

Этот контракт отражает только то, что подтверждено текущей реализацией. Пункты, отмеченные ниже как ограничение, нельзя «обойти» придумыванием близкого синтаксиса.

### Метаданные одной статьи

Передавать каждый материал как отдельную сущность с явными полями:

```json
{
  "task_number": 1,
  "group_key": "arithmetic",
  "position": 1,
  "title": "Название до 200 символов",
  "description": "Краткое описание до 500 символов",
  "read_minutes": 12,
  "status": "draft",
  "content": "Полный UTF-8 текст статьи"
}
```

`task_number` уникален в курсе и после назначения считается стабильным. `group_key` — ключ группы из manifest, а не предположение о внутреннем `group_id`. `position` задаёт порядок внутри группы. `read_minutes` целое 1–180 для API. Передаваемый `content` не должен включать служебный `<!--status:...-->`; API/importer добавляют префикс статуса. Поля `title`/`description` соблюдать по лимитам схемы. Для всего курса отдельно передать course `title` и стабильный ASCII `slug` длиной до 50, затем 15 групп с `name` до 200, `description` до 500 и позициями.

### Разрешённый синтаксис и правила вложенности

1. Основной текст — UTF-8 Markdown: `#`–`######`, абзацы, жирный/курсивный, inline-code, обычные и нумерованные списки, вложенный Markdown-список, стандартные таблицы, цитаты `>`, разделитель `---`, ссылки `[текст](URL)`, fenced code.
2. Для тематического раздела использовать `## Название`; не использовать `[section:...]`.
3. Выделения брать только из раздела 5: `[REMEMBER]`, `[IMPORTANT]`, `[NOTE]`, `[WARNING]`, `[TIP]`, `[INFO]`, `[TRY]`, `[HOW_IT_WORKS]`, `[CALLOUT]`, `[PRACTICE_TASK]`, `[DATA_TYPES]`, `[OPERATIONS]`. Не изобретать имя блока. Не рассчитывать, что вложенный Markdown в теле карточки обработан как основной.
4. Код — fenced Markdown либо `[CODE lang="python"]...[/CODE]`. Исполняемый редактор (`CODE_RUNNER`/`INTERACTIVE code`) использовать только при необходимости Python-демонстрации.
5. Изображение — `![описательный alt](/theory/uploads/... или /static/...)`; сам файл передать отдельно через подтверждённый upload workflow. Подпись — отдельным абзацем. Предпочитать PNG/WebP; SVG только доверенный файл.
6. Формулы допустимы только в ограниченном подмножестве раздела 4: `$...$`, `$$...$$`, простые `^`/`_`, `\\sqrt{...}` без вложенных скобок и подтверждённые команды. Не использовать `\\frac`, системы/cases, матрицы, интегралы, суммы, пределы, неизвестные команды и длинные строки без ручной проверки в текущем UI.
7. `LEVEL`: не использовать 2+ уровней в публикации, пока в той же сборке не подтверждён работающий переключатель. Для одиночного LEVEL пользы нет; предпочтительно обычный текст и `##`-разделы.
8. `CHECKPOINT`: только single-choice, с `question`, `options` через `|`, точным `answer`; задавать уникальный `key` ≤80 символов и опциональные `hint`/`explanation`. В полях вопроса и вариантов формул не использовать. Любой вопрос с числами проверять как строку с точным совпадением.
9. `INTERACTIVE`: допустимые типы и ограничения перечислены в разделе 8. У каждого блока уникальный стабильный `key`. Не обещать математическую эквивалентность, автооценку свободного объяснения, несколько допустимых текстовых ответов или настраиваемый допуск. `explanation` не добавлять в ожидании, что UI покажет его.
10. Не вкладывать LEVEL в LEVEL, интерактив в интерактив, специальный маркер в атрибут или сложную разметку в атрибут `TYPE/OP`. Уровни вложенности, не подтверждённые этим документом, запрещены.
11. Не использовать raw HTML, в том числе SVG inline, `script`, iframe, `<details>` или обработчики событий. Не вставлять контент, полученный от ученика.
12. Не считать `CHECKPOINT` или `INTERACTIVE` условием завершения статьи: прогресс чтения отдельный.

### Рекомендуемый каркас одной статьи

Ниже шаблон использует только подтверждённые блоки. Это структура для автора, не отдельный импортный формат:

````markdown
# [Название материала]

Краткое вступление: чему научится ученик и какой навык ЕГЭ тренируется.

## Что нужно знать

Определение и основное правило обычным текстом. Для короткой формулы использовать только проверенную запись, например $a^2+b^2=c^2$.

[IMPORTANT title="Главное правило"]
Сформулируйте ключевое правило одной-двумя фразами.
[/IMPORTANT]

## Алгоритм решения

1. Первый проверяемый шаг.
2. Следующий шаг.
3. Подстановка результата в исходное условие.

[WARNING title="Типичная ошибка"]
Опишите конкретную ошибку и способ самопроверки.
[/WARNING]

## Пример решения

Дайте условие и полный разбор в нумерованных шагах. Каждое равенство сопровождайте объяснением перехода. Для длинной цепочки не использовать неподдержанные TeX-конструкции.

## Сравнение случаев

| Условие | Действие | Проверка |
|---|---|---|
| Короткий случай A | Шаги A | Итог A |
| Короткий случай B | Шаги B | Итог B |

## Проверьте себя

[CHECKPOINT key="topic-001-cp-01" question="Какой вариант соответствует правилу?" options="Вариант A|Вариант B|Вариант C" answer="Вариант B" hint="Сначала проверьте условие" explanation="Коротко объясните правильный выбор."]

## Мини-практика

[INTERACTIVE type="input" key="topic-001-i-01" prompt="Введите результат вычисления" answer="12" placeholder="Ответ"]

## Итог темы

- Ключевой вывод 1.
- Ключевой вывод 2.

[REMEMBER]
Одна фраза, которую важно унести из статьи.
[/REMEMBER]
````

Автор обязан проверять буквальное совпадение ответа интерактивного поля, содержимое маркерных атрибутов, корректность `key`, неповреждённость обратных слешей и то, что в контенте не осталось неподдержанных TeX-команд.

### Формат передачи статьи агенту для интеграции

Передавать пакет в UTF-8 JSON, а не копировать последовательно содержимое в shell-команду. Для статьи включать приведённые выше метаданные плюс content как JSON string. Для всего пакета: стабильные course `slug`, полный список групп с `key/name/position`, все статьи с 1…174 `task_number`, и `content_sha256` для каждого content, рассчитанный автором/передающей стороной. Отдельно передавать файлы изображений со стабильными именами и mapping `filename → alt → статья/раздел`; не кодировать их в сырой HTML. Не использовать `id` для новой статьи; при обновлении существующей сначала сверить ID и номер курса.

## 13. Известные ограничения

- Math-рендерер не является KaTeX/MathJax и не понимает общий LaTeX.
- Несколько LEVEL могут оставлять часть контента скрытой без работающего переключателя.
- CHECKPOINT принимает только один точный вариант; числовой/символьной проверки нет.
- INTERACTIVE имеет много UI-типов, но большинство ответов проверяется точной строкой; нет толерантного числового или математического checker.
- В API/schema не найден лимит размера `content`, но внешние лимиты upload/proxy/database на огромный пакет **НЕ ПОДТВЕРЖДЕНЫ**.
- Raw HTML не очищается в теоретическом пути; только доверенный авторский контент.
- `/theory/manage` загружает bodies в список управления и имеет побочный эффект при отсутствии группы.
- Стандартный curriculum CLI предметно привязан к информатике, включает модификацию содержимого и сейчас имеет статическое расхождение схемы с пакетными JSON.
- Локальная DB не содержит материал для end-to-end сверки реального наполненного курса.
- Автоматическая подпись, диаграммы, графики, SVG inline, сворачиваемые ответы и rich-text редактор как доказанная функция не обнаружены.
- Прямой маршрут статьи не полностью повторяет последовательное закрытие каталога; не считать последовательность механизмом прав доступа к материалу.
- Обработчики теории глобально исключены из CSRF-защиты Flask-WTF; для будущего пакетного импорта необходима надёжная авторизация преподавателя.

## 14. Риски наполнения большого курса

1. **Отображение математики.** Основной риск. Большая доля профильной математики требует дробей, систем, логарифмов, пределов, сумм, интегралов и случаев, которые текущий рендерер не реализует.
2. **Невидимые уровни.** Несколько `LEVEL` без переключателя создают риск потери большей части материала для ученика.
3. **Потеря связи с прогрессом.** Перенумерация статей после назначения курса может оставить записи состояния/блокировок привязанными к старым task numbers.
4. **Объём админ-страницы.** 174 длинных `Text` могут загружаться целиком в `/theory/manage`; каталог ученика контент не выбирает, но админский экран может стать тяжёлым.
5. **Ошибочная повторная загрузка.** API create отклонит дубль task_number, а слепое создание/смена ключей создаст конфликты или потери состояния. Нужен стабильный manifest и обновление существующих ID.
6. **Информатический импортёр.** Штатный CLI требует предметные номера 1–27 и дописывает Python-лаборатории; для курса математики он изменит авторский контент и не соответствует структуре 174 материалов.
7. **Санитизация.** Raw HTML проходит в шаблон как safe. Пакет не должен включать непроверенный HTML.
8. **Сохранение/сверка.** Unicode/обратные слеши сохраняются текстовым полем, однако в маркерных атрибутах нужны кавычки и корректное JSON-экранирование. Сверять сохранённую строку с исходной обязательно.
9. **Числовая автооценка.** Если автор ожидает, что ученик введёт эквивалентную дробь/десятичную запись, интерактив сочтёт её неверной. Для важных вычислений использовать single-choice или заранее стандартизовать формат ответа и явно сообщить его ученику.
10. **Реальный объём.** 174 × статьи в десятки тысяч символов — это несколько мегабайт текста без изображений. На уровне `Text` и текущего app config это не запрещено, но пределы прокси, сервера и максимальный срок работы импорта **НЕ ПОДТВЕРЖДЕНЫ**. Загружать/проверять разумными порциями и не делать один монолитный запрос без проверки окружения.

## 15. Итоговый вердикт

**В текущем виде система структурно способна хранить курс из 15 групп и 174 больших статей без миграции:** `Course`/`TheoryGroup`/`TheoryBlock` уже поддерживают нужную иерархию, `content` — `Text` без прикладного максимума, API позволяет сохранять draft и обновлять статью по ID. Пакетный импорт как механизм в проекте есть, но готовый CLI специализирован на информатике и для математического курса использоваться напрямую не должен.

**Для полноценной теории профильной математики ЕГЭ-2027 текущая платформа содержательно не готова без ограничений:** встроенный формульный рендерер не поддерживает общий LaTeX, включая `\\frac`, системы/cases, пределы, суммы и интегралы; интерактивные ответы не понимают математическую эквивалентность и числовые допуски; переключатель LEVEL не подтверждён и может скрыть варианты. Автору прямо сейчас следует использовать обычный Markdown, короткие подтверждённые формулы, безопасные статические иллюстрации, single-choice checkpoint и только простые текстовые интерактивы; не публиковать несколько LEVEL, не ожидать математической проверки и не передавать общий LaTeX с ожиданием корректного отображения.

Перед размещением курса необходима отдельная техническая проверка на целевой версии UI: отображение контрольных формул, мобильная ширина, preview всех маркеров, производительность админского списка и тестовый round-trip текста в draft. Это перечисление проверок/ограничений, не предложение реализовывать функции в рамках текущего read-only исследования.
